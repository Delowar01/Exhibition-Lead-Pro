## 7. Order of execution (unchanged discipline: one approved batch at a time; hard stops never improvised around)
**Deployment trigger of record (verified 2026-10-23, batch 14):** `.github/workflows/deploy-dev-vps.yml` runs on every `push` to `develop` (no path filter) and on manual `workflow_dispatch`; its `verify` job (lib declarations, API / web / mobile typecheck, mobile unit tests, API + web production builds) must succeed, then its `deploy` job (only for `refs/heads/develop`; concurrency group `deploy-dev-vps`, `cancel-in-progress: false`) pins the pushed commit on the VPS and runs `docker/scripts/deploy-vps.sh <sha> develop`: ancestry and clean-tree checks, api + web images rebuilt sequentially, the GCS credential readability probe, api + web containers recreated (postgres, the `objectdata` volume and the env file are never touched; no schema command runs), health checks through the loopback gateway, and on a failed health check an automatic rollback of api / web to `previous-deploy.sha` with the job still failing. **A push to `develop` is therefore a deployment.** The B25 inspection workflow (`b25-stage1-inspection.yml`) shares the same concurrency group, so a verifier run and a deployment never execute at the same time, and its own pre-check refuses to start while a deployment is queued or running; GitHub keeps at most ONE pending run per group (a newer queued run replaces an older pending one), so nothing is dispatched while a deployment is queued.
