Implement Batch 3 — Email, Invitations, and Password-Reset Reliability for the existing Lead Capture Pro project.

PURPOSE

Complete and verify the existing email-based user invitation and password-reset flows.

This batch must improve reliability using the current authentication, email queue, templates, provider configuration, database schema, and project conventions.

Do not create a second email system.

CURRENT AUDIT FINDINGS

The current codebase already appears to contain:

- User invitation flow
- Password-reset request and completion routes
- Email templates
- Email queue or worker logic
- SMTP/provider configuration support

Known gaps include:

- Delivery may be skipped when email configuration is missing
- Invitation send and resend reliability is incomplete
- Password-reset delivery is not proven end-to-end
- Failed-send and retry handling are incomplete or unclear
- Browser verification is incomplete

IMPORTANT BOUNDARIES

Do not:

- Redesign authentication
- Replace the existing email provider without a proven reason
- Create a new queue when the current queue can be repaired
- Add unrelated user-management features
- Change tenant isolation or RBAC behavior unnecessarily
- Add social login or SSO
- Expose email tokens, passwords, secrets, or provider credentials
- Log password-reset or invitation tokens
- claim real provider delivery unless an email was actually received
- make unrelated UI changes

STEP 1 — INSPECT BEFORE CHANGING

Inspect the complete current implementation for:

- Invitation creation
- Invitation resend
- Invitation acceptance
- Password-reset request
- Password-reset completion
- Email templates
- Email provider or SMTP configuration
- Email queue and worker
- Retry behavior
- Failed-job handling
- Token storage
- Token expiration
- Token invalidation
- Rate limiting
- Audit logging
- Frontend invitation and reset-password pages
- Existing tests

Identify the exact failure points before modifying code.

Reuse the existing architecture wherever possible.

STEP 2 — PASSWORD-RESET RELIABILITY

Ensure the complete flow works:

1. User requests a password reset.
2. The API returns a safe generic response that does not reveal whether the email exists.
3. A reset token is created securely.
4. The token has an expiration time.
5. The email job is queued.
6. The provider sends the reset email.
7. The reset link opens the existing reset-password page.
8. A valid token allows password replacement.
9. The token becomes unusable after successful reset.
10. Expired, invalid, or previously used tokens are rejected safely.
11. Existing active sessions are invalidated if required by the current security policy.
12. The action is recorded in the audit/security log where the existing system supports it.

Security requirements:

- Never store plain reset tokens if the current schema supports hashed tokens.
- Never return the token through a production API response.
- Never write the token to logs.
- Apply existing request rate limiting or add the smallest targeted rate limit if none exists.
- Avoid email-account enumeration.
- Preserve current password-strength rules.

STEP 3 — INVITATION RELIABILITY

Ensure the complete invitation flow works:

1. An authorized user invites a new organization user.
2. Existing RBAC and permission-subset checks remain enforced.
3. The invitation is tenant-scoped.
4. A secure invitation token is generated.
5. The invitation has an expiration time.
6. The invitation email is queued and sent.
7. The invite link opens the existing acceptance flow.
8. The invited user can create or activate the account.
9. The invitation becomes unusable after acceptance.
10. Expired invitations are rejected clearly.
11. Duplicate invitations are handled safely.
12. Resend invalidates or supersedes the previous token as appropriate.
13. Already-active users are not accidentally re-invited.
14. Failed delivery does not falsely appear as successfully delivered.
15. Invitation and acceptance actions are audited where supported.

The UI should clearly distinguish:

- Invitation created
- Email queued
- Email sent, when delivery confirmation is available
- Delivery failed
- Invitation expired
- Invitation accepted
- Resend completed

Do not promise provider delivery based only on queue insertion.

STEP 4 — EMAIL QUEUE AND PROVIDER FAILURE HANDLING

Repair or complete the existing email delivery path.

Requirements:

- Missing email configuration must produce a clear operational error or disabled state.
- Production must not silently discard required invitation or reset emails.
- Queue jobs must record success or failure.
- Temporary provider failures should retry using the existing job infrastructure.
- Permanent failures must stop retrying after the approved attempt limit.
- Error logs must contain useful provider/error metadata without secrets or message tokens.
- Duplicate processing must not send unnecessary repeated emails.
- Failed sends must be visible to the appropriate administrator or through existing logs.
- Resend must create a controlled new delivery attempt.

Do not build a complex email-delivery dashboard in this batch.

STEP 5 — EMAIL TEMPLATE VALIDATION

Verify the existing invitation and password-reset templates include:

- Correct tenant or Lead Capture Pro branding according to current supported behavior
- Correct recipient
- Correct action link
- Correct expiration information where appropriate
- Safe plain-text and HTML content
- No exposed internal IDs or secrets
- Correct production/staging base URL selection

Do not redesign all email templates.

STEP 6 — FRONTEND FEEDBACK

Update only the existing relevant pages/components as needed.

Ensure:

- Loading states prevent duplicate submissions.
- Success feedback is clear but does not reveal whether an email account exists.
- Provider or queue failures do not show false success to authorized administrators.
- Expired and invalid links display useful messages.
- Resend action has proper loading, success, failure, and cooldown behavior.
- Password reset requires confirmation and validates the password before submission.
- Light and dark theme remain intact.
- Mobile layouts remain usable.
