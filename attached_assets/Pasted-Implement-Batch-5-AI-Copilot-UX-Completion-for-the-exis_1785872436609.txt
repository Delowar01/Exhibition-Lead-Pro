Inspect the actual current implementation for:

- Contact Workspace AI Copilot page
- SalesCopilot and other Copilot components
- AI Assistant conversation UI
- Mobile AI Assistant screen
- Existing AI generation endpoints
- Existing regenerate behavior
- Persisted AI drafts
- Contact notes, activities, interactions, and communication records
- Clipboard utilities

Identify which actions already have backend support and reuse them.

For Save as Note:

1. First check whether an existing contact note, contact activity, interaction, or timeline-note endpoint can correctly store the output.
2. Reuse it when semantically correct.
3. If no suitable contact-note endpoint exists, add the smallest tenant-scoped endpoint using the existing contact activity or interaction model.
4. Do not create a new notes table solely for this action.

STEP 2 — COPY ACTION

Add a visible Copy action to relevant generated AI output surfaces.

Requirements:

- Copy the generated output text to the clipboard.
- Show clear success feedback.
- Show clear failure feedback when clipboard access fails.
- Disable Copy when no generated content exists.
- Preserve formatting as plain text unless the current component already supports rich content.
- Do not copy internal metadata, prompts, IDs, or hidden context.

Cover at minimum:

- Contact Workspace AI Copilot output
- SalesCopilot output where applicable
- AI Assistant generated response actions where the existing design supports them

STEP 3 — REGENERATE ACTION

Add an explicit Regenerate action to generated AI outputs.

Requirements:

- Reuse the existing generation or regeneration API.
- Preserve the selected tool, contact/entity context, tone, language, and user inputs.
- Show a loading state while regenerating.
- Prevent repeated clicks and duplicate requests.
- Keep the previous output visible until the new output succeeds, unless the current design intentionally uses a loading replacement.
- If regeneration fails, retain the previous successful output.
- Show a useful retryable error message.
- Do not create duplicate draft records unless the user explicitly saves the regenerated version.

STEP 4 — SAVE AS NOTE

Add Save as Note for suitable AI outputs.

Requirements:

- Save a real tenant-scoped note/activity associated with the selected contact or supported entity.
- Include the generated content.
- Record the current authenticated user as creator.
- Record the source as AI-generated through existing metadata/custom fields only if the current model supports it.
- Do not store hidden prompts, AI context, tokens, or sensitive provider metadata.
- Prevent duplicate saves caused by repeated clicks.
- Show success and failure feedback.
- Refresh the relevant Timeline or activity view after saving.
- Apply existing RBAC and tenant-isolation checks.
- If the current user lacks note/activity permission, hide or disable the action and enforce denial on the backend.

Do not fabricate a Save as Note action for outputs that have no valid entity context.

STEP 5 — SAVE AS DRAFT

Complete or normalize Save as Draft where existing draft support is available.

Requirements:

- Reuse the existing AI draft persistence service and schema.
- Support the relevant communication type, such as email or WhatsApp.
- Preserve recipient/entity context, subject where applicable, generated content, language, and tool type.
- Saving a draft must not send anything.
- Allow the user to review and edit the draft through the existing workflow.
- Prevent duplicate draft creation from double-clicking.
- Show clear saved, failed, and already-saving states.
- Respect permissions and tenant isolation.

Do not add a new generic draft module.

STEP 6 — EXPLICIT USER CONFIRMATION BEFORE SENDING

Review every AI-generated email and WhatsApp action.

Ensure:

- “Use,” “Apply,” or “Open Draft” does not send automatically.
- The content opens in the existing compose/draft workflow.
- A separate explicit user action is required to send.
- While sending, duplicate send attempts are blocked.
- Existing permission checks remain enforced.
- Tests prove AI-generated communication is not auto-sent.

Do not redesign the communication composer.

STEP 7 — WEB ERROR, LOADING, AND RETRY STATES

Complete error handling in the web Copilot and relevant AI components.

Requirements:

- Handle query and mutation errors explicitly.
- Show a useful message without exposing provider internals, prompts, stack traces, or secrets.
- Provide Retry where the operation is safe to retry.
- Preserve the user’s inputs after failure.
- Preserve the last successful output after regeneration failure.
- Distinguish:
  - Network error
  - Permission denial
  - AI unavailable
  - Validation error
  - Usage/budget limit response already supported by the backend
- Prevent duplicate submissions while loading.
- Disable actions that depend on output until output exists.
- Maintain light/dark theme contrast and responsive behavior.

Do not change backend error contracts unless a confirmed gap prevents correct UI handling.

STEP 8 — MOBILE AI ASSISTANT ERROR FEEDBACK

- Provide a Retry action or allow safe resubmission.
- Do not append a false successful AI response.
- Maintain conversation state after recoverable errors.
- Handle network loss and server error states.
- Keep English and Arabic translations in parity.
- Do not add removed mobile AI intelligence screens.
